# 系统架构

## 总体结构

本项目是一个“博客 + OJ + 判题沙盒”的组合系统，前端统一，后端按服务拆分：

1. `apps/web`  
   Next.js 前端，承载博客与 OJ 页面，统一主题和交互。
2. `kkg-blog-backend`  
   博客核心后端（用户、文章、评论、通知、管理员）。
3. `kkg-oj-backend`  
   OJ 核心后端（题目、提交、判题队列、题解绑定）。
4. `kkg-sandbox`  
   独立判题执行器，当前只支持 Go 代码执行。
5. `deploy/nginx`  
   网关入口：`/blog-api` -> 博客后端，`/oj-api` -> OJ 后端。

## 逻辑边界

1. 博客后端负责：
   - 账号、登录态（博客自身）
   - 博客内容与互动
   - 管理中心与审计

2. OJ 后端负责：
   - 题目、提交、状态流转
   - 判题任务投递（RabbitMQ）与结果入库
   - 题目与博客题解关联

3. 沙盒负责：
   - 接收执行请求
   - 在受限环境中编译/运行
   - 返回运行结果（输出、状态、耗时、内存）

## 关键调用链

1. OJ 提交链路  
   前端提交代码 -> OJ 后端创建提交记录 -> 投递 MQ -> 判题消费者调用 `kkg-sandbox` -> 更新提交状态 -> 前端拉取 / 订阅状态。

2. 博客发布链路  
   前端编辑草稿 -> 博客后端版本化保存 -> 发布后写 ES 索引 -> 首页/搜索可见。

3. 题解联动链路  
   管理员在题目上发起 AI 题解任务 -> OJ 后端生成题解内容并投递到博客接口 -> 博客生成文章 -> OJ 保存题目与文章绑定关系。

## 数据与中间件

1. MySQL：主业务数据（博客 + OJ）。
2. Redis：会话、缓存、排行榜（如 OJ 首次过题 24h 排行）。
3. RabbitMQ：判题任务队列。
4. Elasticsearch：搜索索引（文章、用户、推文）。
5. MinIO：图片对象存储。

## 当前建议

1. 继续保持“前端统一、后端分治”的边界，不在服务间跨库直连。  
2. 所有跨服务调用统一走 HTTP API + 明确鉴权头。  
3. 管理与审计逻辑只放在后端，不在前端做权限假设。
